# NOX NEXT — Human Review Workflow

This document specifies the frontend/product workflow only. It does not create accounts, grant roles, store applicant documents, or change backend behavior.

## 1. Request lifecycle

1. **Received** — a request is submitted through an approved, age-appropriate registration flow.
2. **Under review** — an assigned human reviewer checks only the minimum information necessary.
3. **More information required** — the reviewer records a neutral reason code; the applicant is told what non-sensitive information is missing.
4. **Approved** — the request may proceed only if all applicable eligibility, safety, and platform requirements are independently satisfied.
5. **Rejected** — the reviewer records a reason code and provides an appeal route where appropriate.
6. **Appealed** — a different authorized reviewer reconsiders the decision when staffing permits.

A reviewer must not approve their own request. A second-person review is required for role assignment, account restrictions with significant impact, and disputed decisions.

## 2. Roles

| Role | Permitted workflow access |
|---|---|
| User | Own request status and appeal instructions |
| Reviewer | Assigned review queue and review records |
| Admin | Admin console plus reviewer workflow |
| System service | Server-side eligibility and authorization checks |

Admin access includes review access, but review and admin permissions remain distinct and independently logged. No role is granted by browser storage, client code, or a form field.

## 3. Review record

A future server-side record should contain only:
- Request reference (opaque ID)
- Assigned reviewer account ID
- Review status and decision code
- Short, non-sensitive rationale
- Created/updated timestamps generated by the server
- Previous decision reference when appealed or superseded

Do not put passwords, identity-document images, identity numbers, or unnecessary personal data in review notes or audit logs. If legal identity verification is required, use a separately approved compliant process; do not build document collection into this preview.

## 4. Operational safeguards

- Apply least-privilege access and assignment scoping.
- Require server-side authorization for every queue read and decision write.
- Keep an append-only audit history; corrections create a new event rather than silently rewriting a past decision.
- Rate-limit submissions and review actions.
- Provide an appeal path and conflict-of-interest handling.
- Restrict access to minors' information and collect the minimum necessary data.
- Human review does not override age restrictions, child-safety requirements, applicable law, or professional licensing/ accreditation requirements.
- Do not activate adult-only features or accept a manual review as a substitute for reliable eligibility safeguards.

## 5. Current implementation status

The existing `review-console.html` and `admin-console.html` are static authenticated previews. They do not read applicant records or execute decisions. This document is a product specification only. Backend, database, schema, secrets, runtime, and deployment remain unchanged pending separate explicit approval.
