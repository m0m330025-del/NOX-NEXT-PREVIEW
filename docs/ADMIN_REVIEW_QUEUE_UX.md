# NOX NEXT — Admin Review Queue UX

## Status
Design specification only. This document does not implement authentication, identity verification, age assurance, account approval, or access to restricted areas.

## Purpose
Provide administrators with a clear workspace for reviewing ordinary support requests, user reports, and account-safety appeals. The queue is for moderation and support operations only.

## Admin screen

### Queue overview
Show three counters:
- New requests
- In review
- Resolved

Default list columns:
- Request number (generated by the trusted backend)
- Request category: Support, Report, Account appeal
- Submitted date
- Status
- Assigned moderator
- Last updated

Do not show identity-document images, full document numbers, passwords, session tokens, or other unnecessary sensitive data.

### Request details panel
Display:
- Request number and category
- The user's submitted explanation
- Relevant report reference, if applicable
- Creation and update timestamps
- Internal moderator notes, visible only to authorized staff
- A chronological audit history of status changes

### Allowed actions
- Assign to moderator
- Mark as in review
- Request clarification
- Resolve with a reason
- Reject with a reason
- Escalate to a senior moderator

Every action must be authorized server-side and recorded with the acting staff account, timestamp, action, and reason. The browser must never be trusted to supply the moderator identity.

## Status model
- `new`
- `in_review`
- `needs_information`
- `escalated`
- `resolved`
- `rejected`

Only the backend may change a request's authoritative status.

## Privacy and security requirements
- Require authenticated staff sessions and role-based authorization on every read and write.
- Keep staff-only notes and queue data unavailable to ordinary users.
- Validate request ownership before allowing a user to view their own submitted request.
- Rate-limit submissions and protect against duplicate/spam requests.
- Escape user-submitted text before rendering it in the admin interface.
- Keep an append-only audit trail for staff actions.
- Define retention and deletion rules before production use.
- Never put Appwrite API keys or other secrets in frontend code.

## Explicit exclusions
This queue must not be used as a manual age-checking system, must not store identity-document photos or numbers, and must not grant access to any age-restricted or otherwise protected area. A moderator's decision in this queue is not proof of age or legal eligibility.

## Implementation sequence
1. Approve the UI and request categories.
2. Define a private database schema and staff roles.
3. Implement server-side authorization and audit logging.
4. Add abuse/rate-limit controls and ownership tests.
5. Test with non-production sample requests.
6. Keep all restricted-area access disabled unless a separate, appropriate and independently validated eligibility system is available.
